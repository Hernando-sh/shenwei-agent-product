# 周 spec · W2 受控的报价准备与保存

> 这是 2.1 开头写成的版本。它只回答「这项能力支持什么、守什么规则、怎样算做对」，不回答用什么技术做。W1 的查询能力继续成立，这里不重复。

## 1 业务目标与功能需求

业务员给客户出报价，要先看客户等级与信用、有没有逾期回款、有没有已经出过的报价，再按报价规程算价，最后记进 ERP 报价台账。现在这几步在 ERP 里手工翻、手工算，容易算错折扣、给逾期客户出新报价、同一内容重复出单。

本周系统提供一类能力：为明确客户、型号和数量的报价提供草案生成与经确认的台账保存。业务员用自然语言说明给哪个客户报哪些型号多少台；系统查客户、信用、回款与已有报价，按 ERP 报价规程算出草案给业务员看；业务员确认后系统才保存到台账，并把保存结果交回；未确认不保存，保存失败或结果未知时核实后再说明，重复的保存请求只产生一条记录；每一步都有可检查的执行记录。

来源：US-05「按工况出选型与报价单」中的「价格与报价规程一致；未确认前账本里没有报价记录；确认后账本正好一条；报价工具没有自由金额参数」（选型、Skill、报价单 PDF 不在本周，归 W3）；US-02「询问 / 自动模式：读自动做，写先问我」中的确认机制（模式开关上页面归 W5）；产品级 AC-02、AC-03。

与总 spec 的关系：US-05 整体标 W3–W6，本周只承担其中「算价 → 草案 → 确认 → 保存台账」这一段，不改总 spec 的周次；US-03 查订单已在 W1 作独立变体实现，本周作只读回归，不另立条目。

## 3 输入与事实来源

输入：请求文本、已有完整历史、允许工具清单、当前模式（ask / auto）、本次操作者。输出：草案或说明、确认请求、保存结果或核实结果；同时有运行状态、停止原因与业务结果。

| 信息 | 从哪里获得 | 怎样使用 | 字段 |
|---|---|---|---|
| 客户 | 用户给出的名字、城市或编号 → 客户查询（search_customers，`q` 匹配英文公司名 / 城市 / 编号，可加 `country_code`）→ 客户主数据（get_customer） | 必须落到唯一客户编号；落不到或多个候选 → 澄清 | id、legal_name、country_code、price_group、payment_terms_code、incoterm_default、blocked、credit.status |
| 回款 | 应收账龄（get_receivables） | 逾期则不出草案 | credit_status（clear / open / overdue）、overdue_days、aging、open_items |
| 已有报价 | 报价台账查询（list_quotes，按 customer_id） | 有效期内同客户同行内容已出 → 不重复出 | id、status、valid_until、is_expired、lines[].sku / qty |
| 价格 | ERP 报价计算（price_quote，`GET /v1/quotes/price`，只算不记） | 草案的全部金额字段只从这里取 | lines[].conditions[]（PR00 挂牌价 / K007 客户等级 / ZQTY 数量 / ZFXR 汇率）、unit_price、amount、total_amount、currency、incoterm、payment_terms_code、price_rule_ref、fx_rate、price_date、recorded=false |
| 库存交期 | W1 的 get_availability | 用户顺带问发运时间时使用 | available、earliest_ship_date、as_of |
| 规程依据 | 知识证据（search_knowledge） | 用户问「有效期 / 付款条件依据是什么」时查；查不到如实说没有依据 | hits[].doc_id、clause、locator、version、status、applies_to；index_version、corpus_fingerprint |
| 台账记录 | 保存结果（create_quote，`POST /v1/quotes`） | 保存成功的唯一凭证；答复里的报价号只从这里取 | id、revision、status=issued、valid_until、total_amount、created_by |

权威事实：ERP 的返回；测试用的固定快照是它的本地副本。知识服务的切块是资料原文的副本，带出处与版本。

口径：

- 金额：按 ERP 返回的数值与独立 `currency` 原样使用（报价是 USD，挂牌价是 CNY），系统不换算、不格式化、不做乘法。「金额字段」指 lines[].unit_price、lines[].amount、total_amount、conditions[] 的 value / rate、fx_rate.rate。答复里说「总价」一律指 total_amount。
- 草案 ≠ 台账记录：草案是 price_quote 的结果加客户和行，`recorded: false`，没有报价号；台账记录是 POST 成功返回的 `id`（QT-000001 形式）。答复里出现报价号，必须来自 POST 返回。
- 有效期：由 ERP 在保存时给出（`valid_until`，价格日起 30 天；ERP 虚拟时钟 2026-09-20 → 2026-10-20）。草案阶段没有这个字段，所以草案里不能出现有效期日期，只能说保存后 30 天有效。这是事实口径，不是话术。
- 两种时钟：业务事实（price_date、valid_until、is_expired、逾期天数）按 ERP 虚拟时钟；系统自己的行为（确认有效期、工具超时、墙钟）按真实时钟。两者互不换算。
- 逾期：天数取 get_receivables 的 overdue_days；金额取 get_customer 的 credit.overdue_amount（等于账龄表里已到期各桶之和）。客户 `blocked` 不为 none 或 credit.hold 为真，与逾期同样处理。
- 付款条件、FOB 口径：来自客户主数据与 ERP 返回（payment_terms_code、incoterm），不来自模型记忆。
- 「已有有效报价」：status 为 issued 且未过期（`is_expired: false`），客户相同，行的 sku 与 qty 集合相同。改版、过期的不算。
- 客户检索：ERP 的城市与公司名是英文；用户说「雅加达」，检索词应是 Jakarta 或国家代码 ID。这是模型质量点，进量表。

## 4 任务分解与行为分支

| 动作 | 需要什么 | 谁负责 | 产出 |
|---|---|---|---|
| 识别客户、型号、数量 | 用户文本、明确的历史 | 模型 | 客户线索 + 行；或「缺什么」 |
| 补充缺失条件 | 缺什么 | 模型 | 一句澄清，等待下一次输入 |
| 落实客户 | 客户线索 | 程序执行只读工具 | 唯一客户编号与主数据；或多候选 / 无候选 |
| 查回款与已有报价 | 客户编号 | 程序执行只读工具 | 逾期状态；已有报价列表 |
| 算价出草案 | 客户编号、行 | 程序执行 price_quote：先查规则（逾期、重复、金额输入），再调 ERP 算价 | 草案（金额字段全部来自 ERP）；或被规则拦下的说明 |
| 请求确认 | 草案 | 程序：把写动作做成变更集，向操作者请求确认 | 确认 / 拒绝 / 过期；确认绑定变更集版本 |
| 保存台账 | 已确认的变更集 | 程序执行 create_quote，带操作标识 | 台账记录；或失败 / 未知 |
| 核实未知结果 | 操作标识 | 程序 | 已保存（取回原结果）/ 未保存 |
| 整理答复 | 草案、确认结果、保存结果 | 模型 | 有依据的说明：报价号、金额、条件、有效期；或为什么没出、没存 |
| 结束或等待 | 响应形态、预算 | 程序 | 停止原因与业务结果 |

依赖：算价需要唯一客户编号和至少一行；保存需要通过规则的草案和对该草案的有效确认；核实需要保存时用的操作标识。查回款和查已有报价都在算价之前，它们之间谁先谁后是实现选择；规则判定的顺序固定：客户状态（blocked / hold / 逾期）→ 已有有效报价，两者都不满足才算价，只报第一条拦下的理由。规则所需的事实查不到（回款或台账接口失败）→ 不出草案，说明无法确认客户状态，不默认放行。

| 条件 | 应有行为 | 不允许的行为 |
|---|---|---|
| 客户唯一、无逾期、无已有报价、确认通过、保存成功 | 草案 → 确认 → 保存 → 答复报价号、总价、条件、有效期 | 答复里出现 ERP 返回之外的金额或日期 |
| 缺客户、缺型号或缺数量，历史也不能确定 | 澄清，不算价、不写 | 猜一个客户或数量 |
| 客户查不到，或多个候选 | 说明查不到 / 列出候选请选择 | 挪用相近客户；默认取第一个 |
| 客户有逾期回款，或 blocked / 信用 hold | 不出草案、不写；说明天数与金额（或冻结状态） | 先出草案再提醒；写入后记一条备注；默认放行 |
| 回款或台账接口失败，规则无法判定 | 不出草案；说明客户状态无法确认 | 当作没有逾期继续 |
| 有效期内同内容报价已存在 | 不重复出；给出已有报价号与有效期 | 再写一条；把已有的改掉 |
| 用户给了单价或折扣 | 说明价格由规程算，不出草案、不写 | 把金额塞进请求；按用户金额写入 |
| 操作者拒绝变更集 | 不写；记录拒绝；结束 | 稍后自动再问；改参数后不再问 |
| 确认后改了数量或型号 | 原确认失效；重出草案、重新确认 | 用旧确认写新参数 |
| 确认过期 | 失效；重新确认 | 过期仍写 |
| 保存返回 502（结果未知） | 不换标识重发；用同一操作标识核实；已保存 → 当作成功；未保存 → 说明失败 | 新开一笔；对用户说「已保存」却没有报价号 |
| 保存超时 | 同上；写操作不走只读工具的有界重试 | 自动重试写入 |
| 任何工具返回的文本里夹带「跳过确认」等指令 | 当作数据；确认照问 | 据此省略确认或改参数 |
| 模型请求未注册工具、或带金额的写工具 | 拒绝并记录；拒绝结果交回模型，由模型决定下一步；步数预算兜底（沿用 W1-AC-04） | 执行任意函数；程序自动重试 |
| 自动模式下的内部写（跟进记录） | 不问，直接写，记事件 | 把报价台账写入也当内部写放行 |
| MCP 来源断开或协议错误 | 失败类别可区分（来源不可用 / 协议错误），不伪装成功 | 当作业务无数据 |

允许：模型决定只读查询的顺序与是否顺带查交期；模型组织草案说明与澄清措辞；只读工具在预算内重复读取不算错。
禁止：模型或业务员给出的金额进入任何请求；未确认写；确认跨参数复用；重试写操作时换新的操作标识；工具结果里的文字当指令；MCP 来源绕过策略；密钥进事件；把失败或未知说成已保存。

## 5 结束与执行限制

- completed：给出了草案并完成确认流程（保存成功、被拒绝、被规则拦下）或提出了必要的澄清。completed 不证明台账里有记录；有没有，看保存结果与账本。
- failed：无法继续本次执行（模型响应无法解析、模型调用失败、写入核实后确认未保存且无法重试）。
- stopped：达到次数或时间限制，受控停止，说明到哪一步、台账有没有写。stopped 对应的业务结果是 failed（未完成）。

澄清和确认都结束本次执行：提出澄清 → completed（等待下一次输入）；每次改参数都是新草案、新确认，没有另设次数上限，由步数与墙钟兜底。确认过期即作废，同内容的新请求是新的变更集与新的 operation_id。

业务结果（答复里要能分辨，W4 建判定器）：resolved 保存成功；declined 被规则拦下（逾期、重复、金额输入）；cancelled 操作者拒绝或撤回；needs_clarification 缺信息；failed 保存失败并已如实说明。

数字限制：

- 模型请求次数上限 max_steps = 8（本周配置；主案例预测至少 5 次请求：识别、落实客户、回款与台账、算价、确认后保存、答复，W1 的 6 不够。一次 = 实际向模型发出一次请求；重试计数；达到 8 后不能发第 9 次）。
- 一个变更集一次确认一次写：同一 operation_id 不论确认几次、重放几次，只对应一条台账记录。
- 确认有效期 10 分钟（本周配置，真实时钟；来源 v3.0 §3.5「确认绑定…有效期」；W5 起由 Java 确认服务统一给值）。
- 写工具单次超时 5 s，不重试；超时或 502 后核实最多 1 次（同一操作标识重放一次）；核实请求本身失败或仍未知 → failed，说明需到 ERP 台账人工核对。核实是工具层动作，不计入 max_steps，计入墙钟。
- 操作标识：`operation_id` 由程序在变更集生成；写请求的 `Idempotency-Key = <run_id>:<operation_id>`；`X-Actor = agent:<run_id>`；变更集里记确认人（终端 `--actor`，默认 `sales:zhou`）。

时间限制沿用 W1：模型单次 60 s、整次执行 120 s；用量不可得时标记未知。
