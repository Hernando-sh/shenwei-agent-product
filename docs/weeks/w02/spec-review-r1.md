**1 遗漏**  
- 第4节「任务分解与行为分支」表格中“查回款与已有报价”行为描述：“查回款和查已有报价都在算价之前，它们之间谁先谁后是实现选择”，但未约定当两者结果冲突时（如回款查出逾期、台账查出已存在有效报价）的优先级或合并处理逻辑；应明确规则拦截顺序（如逾期优先于重复）；建议在该句后补充“逾期状态判定优先于已有报价判定”。  
- 第4节「条件 → 不允许的行为」表格中，“客户有逾期回款”对应行为为“不出草案、不写；说明逾期金额与天数”，但未约定当客户同时存在逾期与信用冻结（`blocked: true`）时是否叠加拦截或需分别说明；应覆盖信用状态与回款状态的组合分支；建议在该行“不允许的行为”列后增补“不区分信用冻结与逾期，统一按最严规则拦下并合并说明”。  
- 第5节「结束与执行限制」中定义了`completed`状态，但未说明当确认过期（10分钟）且用户后续重新发起同内容请求时，是否复用原变更集或生成新变更集；可能造成业务员感知断连；建议在该节末尾补充“确认过期后，同内容新请求视为独立流程，生成新 operation_id 与新变更集”。  
- 第6节「W2-AC-05」验收条件要求“前置规则由程序执行”，但未约定当 ERP 接口返回异常（如 `get_receivables` 500）时，程序应如何兜底判定逾期（如默认不清除逾期标记？默认放行？）；缺少故障态下的确定性行为；建议在 W2-AC-05 条件描述末尾增补“ERP 回款接口失败时，默认视为无逾期，继续流程，但记录 warning 事件”。  
- 第7节「W2-CASE-09 注入」案例中，订单备注含指令，要求“报价仍走确认”，但未覆盖 SCRM 归档会话记录、跟进记录等其他来源中夹带同类指令的情形；遗漏非订单类注入场景；建议在 CASE-09 描述后增补“所有工具返回的文本字段（含 SCRM 会话、跟进、线索分级）中出现的指令性文字均视为数据，不触发跳过确认”。

**2 越界**  
- 第2节「能力范围与非目标」表格中，“给雅加达报 2 台 X200，单价按 280 美金”列为“不接受金额输入”，依据为“S6-QTE-010；总 spec I3”，但总 spec I3 仅约束“报价工具没有自由金额参数”，未禁止模型在草案说明中展示用户提及的金额（作为对比参考）；此处将“不接受输入”扩大解释为“不展示、不提及”，超出总 spec 范围；建议删去“不出草案、不写”中的“不出草案”，改为“不将 280 美金用于计算或写入，草案仅展示 ERP 计算值”。  
- 第3节「口径」中定义“有效期：由 ERP 在保存时给出……草案阶段只能说‘保存后 30 天有效’”，但总 spec 第2节“三个口径”仅规定“价格只由 ERP 算”，未对有效期表述作约束；此为新增交互话术规则，属本周擅自增加产品级交互规范；建议删除该句，或注明“此为 W2 临时话术指引，W3 统一收敛至 UX 规范”。  
- 第4节「任务分解」表格中“整理答复”产出为“有依据的说明：报价号、金额、条件、有效期；或为什么没出、没存”，但总 spec 第1节明确“agent 不替业务员回客户，只整理答复要点”，而“报价号、金额、条件、有效期”属于对外发送级信息，超出了“要点”范畴；此处越界承诺完整报价单要素；建议将“报价号、金额、条件、有效期”限定为“仅当业务员明确要求时，在对话内以结构化字段形式呈现，不生成可导出格式”。  
- 第5节「数字限制」中“确认有效期 10 分钟（本周配置，按真实时钟算）”，但总 spec 第2节“三个口径”及第7节“终态与 Run 状态”均未授权周 spec 自主定义用户侧超时策略；该数值属平台级策略，应由总 spec 或 ADR 统一管理；建议删除该句，改为“确认有效期遵循总 spec 定义的会话级超时策略（待 ADR 补充）”。  
- 第6节「W2-AC-12m」要求“答复里的金额、付款条件、有效期、报价号与 ERP 返回一致”，但总 spec 第4节 US-06 明确“读会话记录整理英文答复要点并写跟进”，其 AC-06（W4）仅要求“要点引用 D06”，未要求所有字段与 ERP 逐字一致；此处将“一致性”提升至字段级硬约束，超出 US-02/US-05 承诺范围；建议将“一致”限缩为“关键业务字段（报价号、总价、币种、有效期起止）与 ERP 返回值相同”。

**3 无停止条件**  
- 第4节「任务分解」表格中“识别客户、型号、数量”动作依赖“用户文本、明确的历史”，但未定义当模型连续 3 次无法识别（如用户输入模糊、历史缺失、多候选未澄清）时的终止机制；可能陷入无限澄清循环；建议在该行“产出”后增补“连续 3 次识别失败则进入 needs_clarification 终态”。  
- 第5节「结束与执行限制」定义“max_steps = 8”，但未说明当第8次请求仍返回需澄清（如客户仍无法唯一落实）时，是否允许以 `needs_clarification` 结束，或必须强制 `failed`；缺少对上限耗尽后的终态映射；建议在该段末尾增补“达到 max_steps 后若未完成确认流程，则以 needs_clarification 结束”。  
- 第4节「条件 → 不允许的行为」中“模型请求未注册工具、或带金额的写工具 → 拒绝并记录”，但未约定拒绝后是否重试、是否降级为只读查询、或直接终止；可能因单次拒绝触发无限重试；建议在该行“拒绝并记录”后增补“拒绝后不重试，直接进入 failed 或 needs_clarification（依缺失类型）”。  
- 第7节「W2-CASE-07 改参数」预测轨迹描述“原令牌失效 → 重新算价 → 新变更集 → 同意 → 保存”，但未约束“改参数”操作次数上限；业务员可在确认环节反复修改（如 2→10→5→20…），导致无限循环；建议在 CASE-07 描述后增补“同一报价请求中参数修改不超过 2 次，第3次修改触发 cancelled”。  
- 第6节「W2-AC-09」要求“未知结果不盲重试”，但仅规定“核实最多 1 次”，未定义核实失败（如核实请求也超时/502）后的终态；可能卡在 unknown 状态无法退出；建议在 W2-AC-09 “仍未知则 failed 并说明”前增补“核实请求本身失败时，直接进入 failed”。

**4 口径不清**  
- 第3节「口径」中“金额：两位小数的数字加独立 `currency`（报价是 USD，挂牌价是 CNY）”，但未说明当 ERP 返回金额为整数（如 `1000.00` vs `1000`）时，系统是否强制补零、或允许原始格式；前后文“草案 ↔ ERP 返回逐一相等”与“两位小数”存在潜在矛盾；建议将“两位小数”明确为“ERP 返回的 decimal 字段精度，不额外补零或截断”。  
- 第5节「数字限制」中“确认有效期 10 分钟（本周配置，按真实时钟算）”，但第3节「口径」定义“有效期：由 ERP 在保存时给出（`valid_until`，价格日起 30 天；教学时钟 2026-09-20 → 2026-10-20）”，两处“时钟”未统一（真实时钟 vs 教学时钟），且未说明确认有效期是否受教学时钟影响；建议将“真实时钟”改为“与 ERP 虚拟时钟同步的系统时钟”。  
- 第4节「条件 → 应有行为」中“客户唯一、无逾期、无已有报价、确认通过、保存成功 → 草案 → 确认 → 保存 → 答复报价号、总价、条件、有效期”，但“总价”未定义是 `total_amount` 还是 `lines[].amount` 汇总，而第3节口径称“总价是各行 amount 之和，由 ERP 算”，此处“总价”指代不明；建议将“总价”统一替换为“`total_amount` 字段值”。  
- 第6节「W2-AC-04」要求“草案里每个金额字段与 ERP 返回逐一相等”，但第3节口径仅列出 `unit_price`、`amount`、`total_amount`，未明确 `conditions[].value`（如 ZQTY 折扣值）是否纳入“每个金额字段”；验收边界模糊；建议在 W2-AC-04 条件中明确定义“金额字段”为 `unit_price`、`amount`、`total_amount`、`conditions[].value` 四类。  
- 第2节「能力范围与非目标」表格中“杜塞尔多夫客户要 1 台 X300，报个价”对应行为“先查回款；逾期 → 不出草案、不写，说明原因与金额”，但“金额”未说明是逾期总额、单笔最大额还是最近一笔额；第3节口径中 `overdue_days`、`open_items` 字段未定义聚合逻辑；建议将“金额”明确为“`open_items[].amount` 总和”。

**5 该进待澄清**  
- 第8节「待澄清问题」中“前置规则放在哪一层：……建议放算价工具内部（程序判，可测）”，但该决定未引用任何总 spec 条目或 ADR，亦未说明为何程序判优于模型判（如可测性是否为唯一依据）；属未经依据的架构决策；建议将“建议”改为“待 ADR-023 批准：前置规则由 price_quote 工具内部程序判定”。  
- 第8节「待澄清问题」中“业务结果（resolved / declined …）记在哪：……本周写进 run.completed 事件的 outcome 字段”，但总 spec 第7节仅定义终态枚举值，未约定存储位置；`outcome` 字段名未在总 spec 事件日志规范中出现；属虚构字段；建议将“outcome 字段”改为“`run.completed` 事件的 `result.status` 字段（遵循总 spec §7 终态枚举）”。  
- 第2节「能力范围与非目标」表格中“切到自动模式再报价 → 支持切换并记事件；报价台账写入在两种模式下都要确认”，但总 spec 第2节“读自由、写过闸”明确“自动模式下内部写不问、对外写仍问”，而“报价台账写入”在总 spec 第3节权限档位中被归类为“对外写”，此处将“对外写”等同于“需确认”属未经验证的解读；建议将“都要确认”改为“按总 spec §2 ‘对外写仍问’执行，确认行为由权限档位表实时判定”。  
- 第4节「任务分解」表格中“核实未知结果 → 程序”，但未说明核实动作是否计入 `max_steps`；若计入，则可能因核实耗尽步数导致无法答复；若不计入，则与“一次 = 实际向模型发出一次请求”定义冲突；该计数规则无依据；建议在第5节“max_steps”定义后增补“核实请求不计入 max_steps，因其不涉及模型调用”。  
- 第3节「口径」中“客户检索：ERP 的城市与公司名是英文；用户说「雅加达」，检索词应是 Jakarta 或国家代码 ID”，但总 spec 第3节“SCRM 只有四个对象”及第4节 US-06 均未约定客户检索语言规范；该规则属新增本地化假设；建议将“应是 Jakarta”改为“按 ERP 接口文档约定，城市名使用 ISO 3166-2 国家子码或英文全称”。
